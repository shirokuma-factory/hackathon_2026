# リポジトリの採点基準（最後の確認で、前の点を知らない Opus 2 人に渡す、2026-11-07）

公式の審査基準（`docs/plan/2026-11-07_審査基準とルールの確認.md`）を、第 1 ラウンドの審査員がリポジトリを開いたときの見え方に直したものです。100 点満点で、採点者は根拠のファイルと行を必ず書きます。

## 採点者の役

| 役 | 前提 |
|---|---|
| A 第 1 ラウンドの審査員 | Anthropic の開発者向けの担当。物流の知識は無い。1 作品に 10 分。動画を見たあと、README を上から読み、公開版を 1 つ開く |
| B 初めて使う中小の運送会社の事務の人 | GitHub に慣れていない。README から公開版を開いて、自分の荷待ちの記録で書面を作れるかを試す |

## 配点

| 配点 | 観点 | 満点の条件 | 減点の例 |
|---:|---|---|---|
| 15 | 最初の 1 画面で分かる | README の最初の画面（スクロールなし）で、名前・誰の何の課題か・動画・試す URL が分かる | 動画が下の方にある。URL が開けない |
| 15 | 課題の具体性 | 数字 2〜3 個に出典があり、誰がどの場面で困るかが書いてある | 数字に出典が無い。「中小の荷主」という分類だけ |
| 15 | すぐ試せる | インストール無しで開ける URL があり、開いて 1 分で価値が分かる | 共有された人しか開けない URL。古い版 |
| 20 | Claude Code の使い方 | 機能ごとの回数と理由、Claude Code が無ければできなかったこと、作成者とのやり取りの型が、記録の数字つきで書いてある | 回数が記録と合わない。使っていない機能を使ったと書く |
| 10 | 期間中に作ったことの区別 | 前から持っていた道具と期間中のアプリが分けて書いてあり、コミットで確かめられる | 区別が無い（ルール上の失格の理由になる） |
| 10 | 試行錯誤の跡 | 採点の推移、作り直しの判断、DEVLOG へ、README から 1 回で届く | 文書が多すぎて読む順が分からない |
| 10 | 安心して使える | データを外に送らない作り、セキュリティ診断の結果、データと素材の権利、ライセンス | 権利の表示が無い。診断の結果が無い |
| 5 | 正確さと文の質 | README の数字・URL・ファイル名がすべて実物と合う。日本語が自然 | リンク切れ。翻訳調の文 |

## 止める条件

2 人の指摘が、文言だけ（実物の誤りや、ルール上の問題ではないもの）になったら止めます。各回の点と、重大な指摘の数の推移を `docs/reviews/` に残します。
