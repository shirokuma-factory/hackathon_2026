# 採点の反復（基準 → 新しい採点者 → 直す → また採点）

このリポジトリで 11/4〜11/6 に 30 回近く回した手順を、次も同じ形で回せるようにまとめたもの。実例と点の推移は `docs/CLAUDE_USAGE.md` の「採点の反復」と `docs/reviews/`。

## 1. 基準を作る（本線）

- 材料は作成者の言葉そのもの（例: 「カスタマーになった気持ちで 95 点以上」「So what? にならないように」「地図は飾りではないか」）と、公式の審査基準（`docs/plan/2026-11-03_審査基準と計画の照合.md`）。
- 観点ごとに「配点」「満点の条件」「減点の条件」を書く。満点の条件は、画面・API・ファイルで確かめられる形にする（「分かりやすい」ではなく「開いて 10 秒で 1 文が読める」）。
- 採点者の役を 3〜5 人置く。例: 懐疑的な審査員、中小の運送会社の配車担当、中小の荷主、特定荷主の CLO、事実の確認役。役ごとに「何を見たら納得するか」を書く。
- 減点は配点とは別に置く。一次資料と食い違う数字、出典の無い数字、実在の会社の運賃・空き、言い過ぎ、相関を因果と書いたこと。
- 基準は `docs/plan/` に置き、版を重ねても前の版を消さない。

## 2. 採点する（毎回新しいエージェント）

- 採点者は毎回、新しく起動したエージェント（Opus）にする。前の回の点・指摘・直した内容は渡さない。渡すと点が甘くなる。
- 渡すのは、基準の文書の場所、採点の対象（画面・API・コード・文書）、出力の形だけ。
- 画面は実物を撮って見る（1920×1080 と幅 400px、コンソールの誤りも数える）。文書だけで採点させない。
- 出力の形: 観点ごとの点と理由、減点、役ごとの納得（○△×と理由）、指摘の表（重大度 P0/P1/P2、区分「実データ / 文言」、場所 file:line、起きる状況、根拠）、100 点に届くための直しの順、確信度。
- 結果は `docs/reviews/<日付>_<基準の名前>_r<回>.md` に、そのまま残す。

## 3. 直す（本線が仕様に落とし、coder が実装）

- 指摘を「実データに影響する」と「文言だけ」に分ける。実データの指摘を先に直す。
- 直すことを SPEC の新しい節（例: §33 r4 の残り 14 件）に番号つきで書き、受入条件（G 番号）と試験を対応させる。
- 担当が重ならないように分け、coder ごとに git worktree を作って並行で実装する。主の作業ツリーにマージし、全部の試験を回す。

## 4. 止めどき

- 実データに影響する指摘が 0 件になり、残りが文言だけになった。
- 2 回続けて、点の差が採点者ごとのぶれ（このリポジトリでは ±6〜7 点）より小さい。
- 指摘が「作成者しか決められないこと」（実在の利用者、公開の URL、名前）だけになった。これは作成者に聞く。

止めたときは、残した指摘と止めた理由を採点の推移の文書に書く。

## 守ること

- AI の採点は審査結果の予測ではない。文書にもそう書く。
- 採点者が見つけた数字の食い違いは、採点者の言い分ではなく一次資料で確かめてから直す。
- 点を上げるために、画面や文書で言い過ぎない。「まだできないこと」は消さずに書く。
