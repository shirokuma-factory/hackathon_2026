# 振り分けて、確かめて、必要なときだけ上げる

最も大きいモデルが最良とは限らない。最小で足りる手段から始め、客観的な基準で確かめ、落ちたときだけ上位に上げる。

## 1. Route（本線がルールで決める。エージェントは呼ばない）

| 段 | 内容 | 実行 | 検証 |
|---|---|---|---|
| T0 | 計算、集計、照合、書式の変換 | Python | テスト |
| T1 | 文書、テストだけの変更、数字の転記 | `coder`（Sonnet） | 決定的な確認のみ |
| T2 | 通常の画面・ロジック | `coder`（Sonnet） | 決定的な確認 → Sonnet のレビュー |
| T3 | 認証、削除、マイグレーション、課金、外部送信、個人情報 | `coder`（Sonnet） | 決定的な確認 → `reviewer`（Opus） |

ローカル LLM（`ollama_generate`）に回すもの: 外に出せないデータの要約・分類、大量の下書き、ラベル付け。結果は Claude が抜き取りで確かめる。

## 2. Execute

- Agent ツールにも Workflow の agent() にも、必ず `model` を書く。書かないと本線のモデルを引き継ぐ。
- 仕様には、受け入れ条件、触ってよいファイル、確認コマンドを書く。
- 同じフォルダに書く作業を並行させない。

## 3. Verify（安い順）

1. 決定的な確認: 型検査、テスト、ビルド、E2E、`git diff --check`、改行コード
2. 判断のレビュー: T2 は Sonnet、T3 は `reviewer`
3. 修正後の再レビューは、修正したコミットと指摘の項目だけを見る。ただし一度も全体レビューを通っていない変更は全体を見る

## 4. Escalate

- Sonnet のレビューが確信度「低」か、上げるべきと判断した → `reviewer`
- Sonnet の修正が1回失敗 → 次の修正は Opus
- Opus でも失敗 → その作業を止めてユーザーに聞く
- 検証の指摘が実データに影響しなくなった → ループを止めることを提案し、残した指摘を記録する

## 繰り返す判断はルールにする

同じ判断を何度もするなら、`{when, then, why, evidence}` の形でファイルに書き、Python に当てさせる。モデルは、ルールで書けない判断のときだけ呼ぶ。閾値は勘で置かず、採用済みの実物から測る。

## 記録

各段でどのモデル（またはローカル LLM、Python）が動いたかと、上げた理由を残す。報告には段ごとのモデルの件数を書く。`docs/CLAUDE_USAGE.md` の「振り分けの実績」に転記する。
